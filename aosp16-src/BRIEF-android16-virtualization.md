## ACTIVITY 5 — Android-16 deltas that bite virtualization

1. **`sApplications` static Application cache (LoadedApk L171-172/1427-1443/1491-1495)** + `Slog.wtfStack` on duplicate: hard single-Application-per-package-per-process rule for all internal callers; host's own `Application` instance and the guest's can collide **by package name**, and the second `makeApplicationInner` silently *adopts* the first. (Same in 34 — not new, but the most load-bearing identity coupling.)
2. **`VMDebug.addApplication(packageName)` / `VMDebug.setUserId`** in handleBindApplication (36 L7563-7564; absent in 34) + `ActivityThread.addApplication()` indirection (36 AT L9159; 34 was inline `mAllApplications.add`) — ART now tracks the set of "applications" per process (crash attribution / anr naming). `instrumentWithoutRestart` path also calls `VMDebug.addApplication` (L8101-8103).
3. **`bindApplication` transaction gained `boolean isSdkInSandbox` and `FileDescriptor applicationSharedMemoryFd`** (34→36 param diff; 36 L1304-1333), consumed into `AppBindData.isSdkInSandbox` (L973) and `ApplicationSharedMemory`/`SystemFeaturesCache` init (L1362-1372). Any replay/forgery of the BIND_APPLICATION transaction must match the new 29-arg `IApplicationThread` signature — transaction code ordering shifted; rebase AIDL proxies on 36.
4. **`finishAttachApplication(long startSeq, long timestampApplicationOnCreateNs)`** — IActivityManager signature changed vs 34's single-arg (36 L7870 vs 34 L7036).
5. **SDK-sandbox cache bypass**: `getPackageInfo(...)` uses `Process.isSdkSandbox()` (L3097) / `isSdkSandbox` (L3106) → *uncached* LoadedApk instances per call. Not a host-package gate, but if your engine mimics sandbox-ish processes the caching assumptions break.
6. **Device identity** (new since 15, mandatory in 36): ContextImpl ctor params `deviceId/isExplicitDeviceId`; `mAttributionSource` carries deviceId (L3640); `updateDeviceId` re-validates via VirtualDeviceId (L3238-3264); ActivityThread `mLastReportedDeviceId` (L447), `handleLaunchActivity(..., int deviceId, …)` (L4437), `updateDeviceIdForNonUIContexts` (L6855, called L4452), service propagation (L5272-5281). 7. **AttributionSource chains** are constructed per-context from real uid/pid (L3637-3640) and auto-registered through `PermissionManager` (L3655-3662); `Intent.prepareToEnterProcess(protected, getAttributionSource())` now threaded through receiver/service arg paths (AT L4177-4178, L5308-5309, L5448; LoadedApk Args.runnable). Faking `mAttributionSource` post-ctor means rebuilding + re-registering it.
8. **`getPackageInfo(ai, compat, CONTEXT_INCLUDE_CODE)` throws SecurityException** for foreign-uid code loads (L3045-3062) — performLaunchActivity's null-packageInfo fallback path (L4131) uses exactly this; use `getPackageInfoNoCheck` on 36 like the framework does.
9. **FLAG_HAS_CODE gate in the cache key** (L3146-3147): `includeCode && (flags & FLAG_HAS_CODE)!=0` — a guest ApplicationInfo built without FLAG_HAS_CODE (or uid-mismatched `publicSourceDir`/`splitPublicSourceDirs`, L404/414-417) lands in `mResourcePackages` and later `peekPackageInfo(pkg,true)` misses.

### What the current in-process LoadedApk-hack hits on API 36
- Two-Application impossibility via `sApplications` (same-package collision + wtfStack) — you must host guests under distinct LoadedApk *and* accept one Application per package name, or hook `getClass().getName()=="android"` bypass… there is none.
- ContextImpl's 14-arg private ctor (deviceId/isExplicitDeviceId added since 15) — all ctor reflection/signature shims from 34 break.
- IApplicationThread.bindApplication 29-arg (isSdkInSandbox + applicationSharedMemoryFd added) and `finishAttachApplication(startSeq, tsNs)` — binder transaction replay mismatch.
- `VMDebug.addApplication/setUserId` process-global identity + `Process.setArgV0/DdmHandleAppName/VMRuntime.setProcessPackageName|DataDirectory` are one-shot globals: a second foreign app silently lies about the process.
- performLaunchActivity's fallback `getPackageInfo(..., CONTEXT_INCLUDE_CODE)` SecurityException for foreign uid; cross-package `notifyPackageUse`/`addPackageDependency` binder chatter; `canAccessDataDir()` false → guest dex/native in data dir won't load under real SELinux.
- `initializeJavaContextClassLoader` requires the guest pkg to exist in the *real* PackageManager (swap `sPackageManager` *and* survive `getPackageInfoAsUserCached`'s PropertyInvalidatedCache path).
- FLAG_HAS_CODE / uid-dependent publicSourceDir selection decide `mPackages` vs `mResourcePackages`; stale-`createTimestamp` ApplicationInfo is dropped on the floor.
- Attribution/deviceId/`prepareToEnterProcess` everywhere: guest contexts broadcast host uid/pid with guest package name; server-side (AMS/AppOps/PMS) package↔uid validation unchanged → notifications/FGS/receivers/ContentProvider auth mismatches persist.
- mApplicationInfo final-ish plumbing: setters are gone (`setDataDirInfoLocked` dead; data dirs fixed in `setApplicationInfo`), resources/loaders auto-propagate from the *host-side* Application object.

### What changes if the guest runs in a second process of the same APK
- You get a real bind: `attachApplication` → `bindApplication(AppBindData{guest appInfo, processName…})` with a **real uid** → `mPackages` cache, `sApplications`, `canAccessDataDir()`, `registerAppInfoToArt`, `notifyPackageUse`, AttributionSource (uid+pid+pkg consistent), AppOps — all pass cleanly; no SecurityException paths, no wtfStack, no sPackageManager swap.
- Still one ActivityThread/one `mInitialApplication`/one process-global identity — but now legitimately the *guest's*; `mAllApplications` normally size 1.
- You still must fabricate client-side dispatch (AMS doesn't know the guest): either keep a stub-side fake `IActivityManager`/`IPackageManager` layer, or run a foreground "stub-in-your-AMS" scheme — the `handleCreateService`/`performLaunchActivity` orderings above are your checklist (makeApplicationInner→newApplication→attach→onCreate; token passed to `serviceDoneExecuting`/`setServiceForeground` must exist server-side or FGS/ANR plumbing silently no-ops).
- Same-APK second process = same SELinux app domain and same installed `ApplicationInfo` uid (host's): data dirs can be repointed *before* LoadedApk construction (`setApplicationInfo` is the only writer of the three dir fields), and ContextImpl picks CE/DE flags off `getDataDirFile()` at construction (L3569-3576) — after construction they're locked (`mFlags`, storage booleans).
- ART/crash attribution benefits: `VMDebug.addApplication` + `Process.setArgV0` reflect the guest honestly, so tombstones/logcat/dumpsys stop blaming the launcher.
